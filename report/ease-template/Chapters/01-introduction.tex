\section{Introduction}
\label{sec:introduction}

Open-source package registries have become a cornerstone of modern software
development, giving developers access to millions of reusable
components~\cite{duan2021supply}. The same accessibility, however, makes
these ecosystems an attractive target for supply-chain attacks: adversaries
inject malicious code into widely used libraries or publish deceptive
packages that imitate legitimate ones~\cite{huang2024spiderscan,
guo2023pypi, liang2021malicious}. Unlike traditional vulnerabilities, which
stem from inadvertent errors, malicious packages are deliberately engineered
to deceive users, which makes them particularly difficult to
detect~\cite{ease2025rag}. Empirical studies show that such packages persist
in registries despite existing safeguards~\cite{guo2023pypi,
liang2021malicious, ohm2020backstabber}, and the continued growth of the
Python ecosystem keeps expanding the attack surface.

Automated detection of malicious packages has traditionally relied on static
and dynamic analysis and on machine-learning classifiers over hand-crafted
features~\cite{singh2021survey}. More recently, large language models (LLMs)
have been applied to security-oriented code analysis, including malicious
package detection~\cite{zahan2024npm, ease2025rag}. LLMs can reason over
source code in natural language and surface subtle indicators of malicious
behavior, yet they are also prone to hallucination and to missing attacks
whose code looks innocuous~\cite{ullah2024llmsec, ease2025rag}.

Retrieval-augmented generation (RAG) has been proposed as a general remedy
for such LLM shortcomings: before answering, the model conditions on
documents retrieved from an external corpus~\cite{lewis2020rag,
gao2023ragsurvey}. Within security, RAG has been used to detect
vulnerabilities in smart contracts~\cite{yu2024smartcontract}, to augment
LLM-based vulnerability detection with knowledge derived from
CVEs~\cite{du2024vulrag}, and to support related analyses. The most direct
prior study of RAG for malicious PyPI package detection, however, reports a
negative result: Ibiyo et al.~\cite{ease2025rag} found that augmenting LLMs
with knowledge bases built from YARA rules, GitHub security advisories, and
malicious code examples did not reliably improve detection, while few-shot
learning was markedly more effective~\cite{ease2025rag}. That study coupled
retrieval to specific knowledge sources and a single retrieval mechanism, so
it remains unclear whether retrieval is fundamentally unhelpful for this task
or whether \emph{how} retrieval is performed---sparse, dense, hybrid,
behavior-based, or contrastive---is what determines its value.

In this paper, we address this question through a controlled comparison of
seven pipelines that differ only in the retrieval strategy: no retrieval,
dense, sparse (BM25), hybrid fusion, behavior-summary, contrastive, and
behavior-summary plus contrastive. We use the same LLM backbone, prompting,
and code-only knowledge base throughout, and evaluate on 1{,}020 test
packages of a standard malicious/benign PyPI benchmark. Our main findings
are:

\begin{itemize}
    \item Code-level retrieval substantially improves detection over the
    no-retrieval baseline, driven by a large recall gain.
    \item Sparse retrieval performs on par with dense retrieval, at a
    fraction of the infrastructure cost.
    \item Contrastive retrieval, which shows the model both malicious and
    benign reference examples, sharply reduces false alarms.
    \item Retrieval over AST-derived behavior summaries is lossy and hurts
    performance, falling below the no-retrieval baseline.
\end{itemize}
