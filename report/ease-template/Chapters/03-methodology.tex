\section{Methodology}
\label{sec:methodology}

% \subsection{Overview}
% \label{sec:method-overview}

We study whether, and how, retrieval-augmented generation (RAG) improves an
LLM's ability to detect malicious PyPI packages, by comparing seven controlled
Llama configurations that differ only in the \emph{retrieval strategy} they apply before
the final classification. At a high level, each Llama configuration
(1)~takes the target package's \texttt{setup.py} source as input,
(2)~builds a query representation from it,
(3)~optionally retrieves reference examples from a knowledge base of
previously seen packages,
(4)~feeds the target together with the retrieved evidence (if any) to an
instruction-tuned LLM, and
(5)~asks the model for a structured verdict: malicious or benign, a confidence
score, security-relevant behaviors with source-line citations, and a rationale.
Figure~\ref{fig:pipeline} illustrates the pipeline.

\subsection{Retrieval Strategies}
\label{sec:retrieval}

The seven Llama methods share the same knowledge base: the raw
\texttt{setup.py} sources of the training packages, indexed in separate
malicious and benign pools. For single-pool retrieval methods, we retrieve
$k=3$ examples. Contrastive retrieval retrieves $k=3$ examples from each
class, resulting in six retrieved examples; the contrastive condition
therefore also has a larger evidence budget, even though the generator and
decoding configuration are fixed. The seven Llama methods are:

\begin{itemize}
    \item \textbf{No RAG.} The target source is classified directly,
    without any retrieved context. This is the controlled baseline.
    \item \textbf{Dense.} The query is embedded with a sentence embedding
    model and matched by cosine similarity against the embedded training
    documents. We use the \texttt{Qwen3-Embedding-4B} model~\cite{qwen3emb}
    and a FAISS \texttt{IndexFlatIP} store over L2-normalized
    vectors~\cite{vllm2023}.
    \item \textbf{BM25.} Sparse lexical retrieval with the Okapi BM25
    scoring function~\cite{bm252009}; no learned components.
    \item \textbf{Hybrid.} Dense and BM25 rankings are fused with Reciprocal
    Rank Fusion~\cite{rrf2009}, $\sum_r 1/(60 + \mathrm{rank}_r(d))$; no
    fusion weights are trained.
    \item \textbf{Behavior.} The target is represented by a static behavior
    summary---imports, suspicious API calls, and behaviors such as shell
    execution, network access, dynamic execution, or base64 decoding,
    extracted with Python's \texttt{ast} module---and dense retrieval runs
    over behavior summaries of the malicious pool, analogous to the AST
    descriptions used in the original dataset.
    \item \textbf{Contrastive.} Dense retrieval is run twice: top-$k$
    documents from the malicious pool \emph{and} top-$k$ from the benign
    pool, and both groups are shown to the model with explicit
    \texttt{MAL}/\texttt{BEN} markers.
    \item \textbf{Behavior + contrastive.} Behavior-summary queries combined
    with dual-pool contrastive evidence.
\end{itemize}

\subsection{Llama Retrieval-Suite Configuration and Prompting}
\label{sec:llm-config}

Classification is performed by \texttt{Llama-3.1-8B-Instruct}~\cite{llama3}
served through an OpenAI-compatible vLLM endpoint~\cite{vllm2023}. Generation
uses temperature $0$ and a maximum of 1{,}024 output tokens. The system prompt
instructs the model that it is performing static source-code analysis, not to
assume behavior unsupported by the source or retrieved evidence, and that
retrieved examples are references rather than proof; every claimed behavior
must cite target source lines. The target source is line-numbered before it is
embedded in the prompt. The output schema is enforced as JSON and requires
\texttt{verdict} (malicious/benign), \texttt{confidence},
\texttt{behaviors} (a list of \{type, evidence\} objects) and
\texttt{rationale}. Retrieved documents are labeled with stable identifiers
(\texttt{MAL\_*} / \texttt{BEN\_*}) and their retrieval scores.

\subsection{Jev No-Retrieval Comparators}
\label{sec:jev-method}

Jev is a \emph{System One} model by TypeSafe AI~\cite{typesafe2026jev}:
instead of generating text, it returns typed, calibrated answers to typed
questions supplied with a state. Appendix~\ref{app:prompts} details the model
class, its question primitives, and the exact request shapes; we access it
through OpenRouter~\cite{openrouterjev} under the pinned identifier
\texttt{typesafe/jev-1.13}.

We use Jev as two no-retrieval comparators. Neither retrieves documents, uses
the training corpus, or generates free-form rationale text.
The \textbf{direct Jev} comparator receives only the target
\texttt{setup.py} as untrusted source evidence and selects a typed
\texttt{malicious}/\texttt{benign} decision. It returns the selected label,
the probability distribution, and confidence.

The \textbf{behavior-guided Jev} comparator uses two calls. First, it asks 12
independent typed yes/no behavior questions aligned with the static vocabulary:
shell execution, process creation, network access, file write/delete, dynamic
execution, environment access, base64 decoding, remote download, persistence,
obfuscation, and credential access. A behavior is marked present when its
probability is at least 0.5. Second, Jev receives the target source, the full
behavior-probability vector, and the thresholded indicators before making the
same typed binary classification. The two calls are required because questions
within one Jev request cannot consume one another's answers. This is a
prompt-and-model-family comparison, not a controlled retrieval ablation: it
changes the model, serving stack, output interface, and, for the second
variant, the input representation.

\subsection{Implementation and Reproducibility}
\label{sec:implementation}

The pipeline is implemented in Python 3.12 as a modular package
(retrieval, static analysis, prompting, evaluation modules) without
framework dependencies; BM25 uses \texttt{rank-bm25}, dense indexes use
\texttt{faiss}, and LLM/embedding calls go through a single
OpenAI-compatible client so that any endpoint can be swapped by environment
variables. All LLM responses, embeddings, and retrieval results are cached
(SQLite) keyed by prompt hash, sample content, evidence IDs, and generation
parameters; retrieval indexes are persisted on disk; and every run records
its configuration, seed, model IDs, and git commit. Run scripts for the seven
Llama methods and both Jev comparators, the evaluation code, and raw per-sample
outputs are included in the replication package. Jev runs are persisted as resumable JSONL files with the
typed responses, resolved model identifier, token usage, latency, cost, and
explicit failures; the behavior-guided run also stores every behavior
probability and its fixed 0.5 threshold.
